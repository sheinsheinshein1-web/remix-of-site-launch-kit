# Производители «Много места»: архитектура, правила и порядок работы

Статус документа: обязательная инструкция для разработки и наполнения.

Этот документ отвечает на два вопроса:

1. Как сайт устроен сейчас и почему точечные правки иногда расходятся между страницами.
2. Как довести систему до состояния, в котором производитель добавляется один раз, а все публичные представления строятся автоматически.

## 1. Главный принцип

> Производитель, его проекты, отзывы, юридические сведения и источники вводятся по одному разу. Компоненты ничего не додумывают и не содержат исключений по названию или `id` компании.

Изменение канонической записи должно автоматически обновлять:

- главную страницу;
- список производителей;
- региональные страницы;
- поиск и избранное;
- карточку производителя;
- карточки проектов;
- рейтинг и количество отзывов;
- метаданные и JSON-LD;
- пререндер;
- sitemap.

Если для изменения одного факта приходится редактировать два места, это дефект архитектуры.

## 2. Нужно ли переписывать проект с нуля

Нет. Публичные URL, компоненты каталога, карточки проектов и большая часть данных уже пригодны для постепенной миграции.

Нужен не новый сайт, а завершение начатой нормализации:

```text
сырьё и источники
        ↓
проверенные записи Manufacturer и Project
        ↓
единые селекторы и ViewModel
        ↓
UI, SEO, JSON-LD, пререндер и sitemap
```

Работа ведётся по частям. После каждого этапа текущий сайт должен собираться и сохранять существующие URL.

## 3. Что есть сейчас

### 3.1. Каталог — файловый, а не серверный

Производители и проекты хранятся в TypeScript и включаются в клиентскую сборку:

- `src/data/manufacturers.ts` — канонические данные производителей;
- `src/data/projects.ts` — основной массив проектов и совместимые производные структуры;
- `src/data/manufacturerCatalogProjects.ts` — компактные каталоги новых производителей;
- `src/data/regionalBatchProjects.ts` — региональные пакеты проектов.

Это означает:

- административной панели для каталога пока нет;
- изменение данных требует изменения файла и новой сборки;
- браузер не получает производителей из базы данных по API;
- бэкенды заявок, обратного геокодирования и чатов не являются бэкендом каталога.

Файловая модель допустима на текущем объёме, если публикация полностью валидируется и автоматизирована. CMS можно подключить позже к той же доменной модели.

### 3.2. Что уже централизовано

- У проекта есть `manufacturerId`, а не полная копия производителя.
- Каноническое название, логотип, сайт, адрес, проверка и внешний рейтинг находятся в реестре производителей.
- Главная, список производителей, региональные страницы, карточки проектов и SEO уже читают значительную часть данных из общего реестра.
- Есть Zod-валидация, тесты связей, пререндер карточек производителей и генерация sitemap.
- Производственные карточки используют общий `ManufacturerProfile`.

### 3.3. Что ещё не завершено

- `ManufacturerProfile.tsx` всё ещё слишком большой и самостоятельно соединяет данные, генерирует SEO-summary и решает, какие пустые состояния показывать.
- `projects.ts` остаётся крупным файлом и одновременно выполняет роль хранилища, адаптера и набора селекторов.
- Страницы напрямую читают `projects`, `makersById` и `manufacturerRegistry`, вместо одного слоя ViewModel.
- Пререндер извлекает маршруты из исходного TypeScript через AST, а не получает готовый валидированный манифест.
- Публичность проекта частично определяется значением `technology`; это должно быть отдельное поле статуса публикации.
- В репозитории остаются старые, лабораторные и концептуальные страницы. Они не должны влиять на production-контракт.
- `sourceAudit` содержит редакторские заметки, но раньше отдельные компоненты могли показывать их посетителю.
- Нет одной команды, которая создаёт черновик производителя, проверяет полноту и формирует отчёт перед публикацией.

## 4. Разделение данных

Нельзя хранить в одном поле публичный текст и внутреннее доказательство.

### 4.1. Manufacturer

Каноническая запись производителя должна содержать:

```ts
type Manufacturer = {
  id: string;
  slug: string;
  publicationStatus: "draft" | "review" | "published" | "suspended" | "archived";

  identity: {
    name: string;
    initials: string;
    logo?: Asset;
    logoFit: "contain" | "cover";
    logoBackground: "light" | "dark" | "transparent";
    verified: boolean;
  };

  positioning: {
    headline: string;
    intro: string;
    technologyLabel: string;
    publicAbout: string[];
  };

  contacts: {
    siteUrl?: string;
    phone?: string;
    email?: string;
    telegram?: string;
  };

  locations: Location[];
  legal?: LegalDetails;
  reviewSources: ReviewSource[];
  builtObjects: BuiltObject[];
  social: SocialSource[];
  seo: ManufacturerSeo;
  audit: ManufacturerAudit;
};
```

### 4.2. Project

Проект хранит только собственные сведения и ссылку на производителя:

```ts
type Project = {
  id: number;
  slug: string;
  publicationStatus: "draft" | "review" | "published" | "archived";
  manufacturerId: string;
  productType: "house" | "bath" | "house-bath";
  useCases: BusinessUseCase[];
  name: string;
  price?: Money;
  area?: number;
  rooms?: ProjectRooms;
  construction?: ProjectConstruction;
  gallery: ProjectAsset[];
  deliveryRegionIds: string[];
  publicDescription?: string[];
  sourceAudit: ProjectAudit;
};
```

В проекте запрещено повторять:

- название производителя;
- логотип;
- рейтинг компании;
- юридические данные;
- адрес производства;
- статус проверки производителя.

### 4.3. Публичный контент и аудит источников

`publicAbout`, `publicDescription`, подписи и пустые состояния видит посетитель.

`audit` и `sourceAudit` видят только редактор, валидатор и отчёт проверки. В них хранятся:

- URL политики конфиденциальности;
- доказательство связи бренда с ИП или ООО;
- найденные, но не импортированные страницы;
- причины исключения дублей;
- сведения о 404, sitemap и ходе импорта;
- спорные совпадения организаций и картографических профилей.

Содержимое `sourceAudit.note` запрещено выводить в публичном React-компоненте. Публичное пустое состояние формируется только из статуса и утверждённого словаря интерфейса.

## 5. Единый слой чтения

Компоненты не должны самостоятельно фильтровать общий массив или соединять сущности.

Разрешённые точки чтения:

```ts
getManufacturer(id)
getPublishedManufacturers()
getProject(id)
getPublishedProjects()
getManufacturerProjects(manufacturerId)
getManufacturerRating(manufacturerId)
getManufacturersByRegion(regionId)
getManufacturerCardViewModel(manufacturerId)
getManufacturerProfileViewModel(manufacturerId)
getProjectCardViewModel(projectId)
getProjectDetailViewModel(projectId)
```

ViewModel возвращает уже готовые данные для UI:

- правильное название и логотип;
- рассчитанное количество проектов;
- вкладки «Дома», «Бани», «Для бизнеса»;
- рейтинг и подпись количества отзывов;
- утверждённый публичный summary;
- доступные секции и их публичные состояния;
- canonical, Title, Description и JSON-LD.

Внутри страницы не должно быть `projects.filter(...)`, ручного подсчёта рейтинга или генерации текста из сырых полей.

## 6. Правила карточки производителя

Все production-карточки используют `ManufacturerProfile` и одинаковый набор секций:

1. Идентичность и основное действие.
2. О компании.
3. Проекты.
4. Юридическая информация.
5. Выполненные объекты.
6. Производство или офис на карте.
7. Отзывы.
8. Социальные сети.
9. Связанные проекты.

Различается наполнение, а не композиция.

### 6.1. SEO-summary

Для заполненного производителя раскрытый summary должен содержать 4–6 содержательных абзацев и закрывать:

- кто компания и где работает;
- какие дома, бани или коммерческие объекты выпускает;
- серии, площади, цены и планировки;
- технологии и подтверждённые особенности комплектаций;
- сценарии использования;
- производство, объекты, отзывы и доступные способы сравнения.

Первый абзац остаётся видимым. Остальные раскрываются через «Подробнее», но присутствуют в исходном HTML.

Запрещены:

- повторение одной ключевой фразы ради SEO;
- перечисление неподтверждённых характеристик;
- текст про импорт, sitemap, 404, перенос изображений и будущие этапы;
- фразы «в каталоге» в каждом абзаце;
- автоматическая замена редакторского текста без проверки результата.

Автоматически допустимо подставлять только проверяемые агрегаты: количество проектов, диапазон площадей, минимальную цену, фактические типы объектов и число отмеченных бизнес-сценариев.

### 6.2. Типы проектов

- `productType: "house"` → «Дома».
- `productType: "bath"` → «Бани».
- `productType: "house-bath"` → «Дома», если это жилой комплекс с баней.
- `useCases` добавляет проект во вкладку «Для бизнеса» и не меняет его фактический тип.
- Обычный дом не становится бизнес-проектом только потому, что теоретически его можно сдавать.
- Бизнес-сценарий добавляется только при наличии подтверждения в источнике или явного продуктового назначения.

### 6.3. Юридическая информация

Юридическое лицо или ИП привязывается только при подтверждённой связи с брендом.

В публичном блоке показываются:

- полное наименование;
- ИНН;
- ОГРН или ОГРНИП;
- статус;
- дата регистрации;
- руководитель или предприниматель;
- юридический адрес;
- основной вид деятельности;
- согласованные реестровые показатели;
- дата проверки;
- только государственные реестры.

Сайт производителя, политика конфиденциальности и публикации, которыми подтверждалась связь бренда с юрлицом, остаются внутренними источниками аудита.

Если связь не доказана, реквизиты не угадываются. Секция остаётся на месте с нейтральным публичным статусом.

### 6.4. Отзывы

- Внешний рейтинг принадлежит производителю, а не проекту.
- Главная, список компаний, профиль и карточки проектов читают один `ReviewSource`.
- Отзывы с сайта производителя не считаются независимым рейтингом.
- Профиль Яндекс Карт подключается только после совпадения сайта, телефона, адреса или юридической сущности.
- Вкладки «Яндекс» и «Много места» сохраняются всегда.
- Рейтинги разных площадок не усредняются.
- Текст чужих отзывов не копируется в собственную разметку; используется разрешённый официальный виджет.

### 6.5. Изображения

- Один Asset содержит URL/файл, ширину, высоту, тип, alt, fit и признак размытого фона.
- Логотип везде выводится через `ManufacturerLogo`.
- Реальные фотографии, рендеры и планировки различаются явно.
- Планировка не получает размытую подложку.
- Карточка сначала загружает одно изображение; остальные — при взаимодействии.
- В публичном тексте не сообщается, что изображения «ещё не перенесены».

## 7. Публикационный процесс

### Шаг 1. Создать черновик

Одна команда должна создавать:

```text
content/manufacturers/<id>/manufacturer.json
content/manufacturers/<id>/projects.json
content/manufacturers/<id>/assets/
content/manufacturers/<id>/audit.json
```

Пока такой команды нет, те же логические части заполняются в текущих TypeScript-реестрах, но статус должен оставаться `draft`.

### Шаг 2. Собрать официальные данные

Проверить:

- весь каталог и пагинацию;
- страницы «другие проекты»;
- контакты и производство;
- политику конфиденциальности и оферту;
- портфолио;
- Яндекс Карты;
- YouTube и Telegram;
- актуальность каждого URL.

### Шаг 3. Нормализовать проекты

- удалить дубли одного проекта с разными URL;
- определить `productType`;
- отдельно определить `useCases`;
- не заполнять неизвестные характеристики;
- указать источник каждого проекта;
- проверить изображения и планировки.

### Шаг 4. Проверить юридическую связь

Сначала установить оператора официального сайта, затем сопоставить его с государственными реестрами. Совпадение только по похожему названию недостаточно.

### Шаг 5. Подготовить публичный текст

Редакторский summary пишется из подтверждённых данных. Автоматические агрегаты вставляет ViewModel. Внутренние заметки не копируются в публичный текст.

### Шаг 6. Запустить предпросмотр

Для каждого производителя проверить:

- мобильную и десктопную ширину;
- светлую и тёмную тему;
- логотип;
- вкладки проектов;
- раскрытие текста;
- юридический блок;
- галерею;
- карту;
- отзывы;
- пустые состояния;
- якорную навигацию.

### Шаг 7. Перевести в `published`

Публикация разрешается только после прохождения автоматического release gate.

## 8. Автоматические запреты и release gate

Сборка должна падать, если:

- `manufacturerId` проекта не существует;
- повторяются `id` или slug;
- опубликованная компания не имеет проектов;
- количество проектов не совпадает с аудитом каталога;
- рейтинг существует без провайдера, URL и даты проверки;
- `sourceAudit.note` передан в публичный компонент;
- публичный текст содержит `sitemap`, `404`, «импорт», «перенос» или редакторские инструкции;
- юридический источник не входит в белый список государственных реестров;
- бизнес-вкладка строится из предположения, а не из `useCases`;
- в карточке производителя больше одного H1;
- canonical, Organization, WebPage, BreadcrumbList или ItemList расходятся с записью;
- опубликованный маршрут отсутствует в пререндере или sitemap;
- логотип выведен в обход `ManufacturerLogo`;
- production-компонент содержит условие по конкретному `manufacturerId`.

Обязательные команды перед деплоем:

```bash
pnpm lint
pnpm test
pnpm build
pnpm test:e2e
pnpm check:manufacturer-prerender
```

Внешние iframe карты и отзывов проверяются отдельным тестом и не должны блокировать локальную разработку при сетевой ошибке:

```bash
pnpm test:e2e:external
```

## 9. Как должен формироваться sitemap

Текущий AST-разбор TypeScript является переходным решением.

Целевой вариант:

1. Build-скрипт импортирует данные и прогоняет Zod-валидацию.
2. Из опубликованных сущностей создаётся `dist/content-manifest.json`.
3. Один и тот же манифест используется для пререндера и sitemap.
4. UI-тест сравнивает публичные маршруты с манифестом.

Ни regex, ни AST не должны повторно реализовывать правила публичности каталога.

## 10. Порядок рефакторинга без остановки разработки

### Этап A. Защитить текущий контракт

- Добавить тесты запрещённого публичного текста.
- Проверять единый рейтинг на всех поверхностях.
- Проверять одинаковый логотип и название.
- Проверять вкладки и пустые состояния всех аудированных производителей.
- Добавить запрет условий по `manufacturerId` в production-компонентах.

### Этап B. Вынести ViewModel

- Перенести подсчёты из `ManufacturerProfile` в `getManufacturerProfileViewModel`.
- Перенести группировку проектов в селектор.
- Перенести формирование публичного summary из React в контентный слой.
- Перевести главную, регионы, каталог и карточки на общие селекторы.

### Этап C. Разделить крупные файлы

- Один файл/JSON-пакет на производителя.
- Один каталог проектов на производителя.
- Общий индекс только импортирует и валидирует пакеты.
- `projects.ts` перестаёт быть ручным монолитом.

### Этап D. Ввести явную публикацию

- Добавить `publicationStatus` компании и проекта.
- Отказаться от скрытия по значению технологии.
- Списки, поиск, sitemap и пререндер используют только `published`.

### Этап E. Создать CLI импорта

Команды:

```bash
pnpm manufacturer:new <id>
pnpm manufacturer:validate <id>
pnpm manufacturer:preview <id>
pnpm manufacturer:publish <id>
pnpm manufacturer:audit-report <id>
```

CLI не публикует автоматически найденные данные. Он создаёт черновик, показывает конфликты и требует подтверждённые поля.

### Этап F. Перевести сборку на манифест

- Удалить дублирование логики маршрутов в prerender.
- Генерировать sitemap из валидированного manifest.
- Добавить проверку полного совпадения UI, prerender и sitemap.

### Этап G. Решить вопрос CMS

CMS подключается только после стабилизации схемы и release gate. Она должна записывать данные в ту же модель, а не вводить второй формат.

## 11. Что запрещено делать дальше

- Создавать отдельный компонент под конкретного производителя.
- Добавлять `if (manufacturerId === "...")` для production-поведения.
- Копировать рейтинг в проект.
- Писать юридические реквизиты в тексте проекта.
- Использовать `sourceAudit.note` как публичный текст.
- Скрывать секцию только потому, что она не заполнена.
- Придумывать характеристики по фотографии или названию.
- Отмечать обычный дом «для бизнеса» без подтверждённого сценария.
- Править sitemap вручную.
- Сообщать, что производитель полностью добавлен, пока release gate не прошёл.

## 12. Definition of Done для одного производителя

Производитель готов только если:

- существует одна каноническая запись;
- все актуальные проекты импортированы или явно исключены в аудите;
- нет копий компании внутри проектов;
- типы «Дома» и «Бани» разделены;
- бизнес-сценарии подтверждены;
- логотип одинаков на всех страницах;
- рейтинг одинаков на всех страницах;
- юридическая связь подтверждена или честно отмечена как неподтверждённая;
- публичный SEO-summary полный и не содержит внутренних заметок;
- все секции используют общий шаблон;
- мобильный и десктопный smoke-test пройден;
- canonical, JSON-LD, пререндер и sitemap совпадают;
- lint, unit, build и E2E проходят.

## 13. Definition of Done для всей платформы

Система готова к масштабированию, когда тестового производителя можно добавить через один пакет данных, не меняя React-компоненты, ручные списки маршрутов и SEO-код. После публикации он автоматически появляется во всех предусмотренных местах с едиными названием, логотипом, рейтингом, проектами, регионами и метаданными.

## 14. Универсальный импорт официальных сайтов

Один производитель:

```bash
pnpm manufacturer:import <id> --write
pnpm manufacturer:gate <id> --write
```

Весь городской срез:

```bash
pnpm manufacturer:batch --city=Екатеринбург
```

Импортёр определяет семейство сайта (Tilda, WordPress, Bitrix или обычный HTML), обходит указанный раздел каталога и sitemap, извлекает поля эталонных карточек Платформы и Bygge и сохраняет доказательство для каждого значения. Правила не содержат условий по id производителя.

Результат всегда сначала записывается в `content/manufacturers/<id>/` как черновик. Не найденное официально поле получает `not-published`, а не выдуманное значение. `release-gate.json` блокирует пакет при конфликте источников, изменении ожидаемого количества проектов, пустом минимальном наборе проекта, недостаточной галерее, дублях URL, названий или главных изображений. Пакетная команда запускает каждого производителя в отдельном процессе, поэтому HTML одного крупного сайта не накапливается в памяти при обработке сотен компаний.

Сводный отчёт сохраняется в `outputs/manufacturer-import-batch.json`. Эти команды не меняют публичный реестр автоматически: перенос в `src/data/generated/catalog-registry.json` остаётся отдельным явно подтверждаемым этапом публикации.
