# Локальный runtime: Astra → Scout

## Дополнение: Сборщик данных

Подключён отдельный вызов `POST /__agent-runtime/collections` с `{sourceRunId, requestId}`. Astra выбирает максимальную confidence из сохранённого успешного результата Scout; при равенстве сохраняется исходный порядок. Поиск Scout не запускается повторно. Новая подзадача `collector` использует те же tasks/runs/events, handoff, Activity, Replay и просмотр JSON.

`server/agent-runtime/collector.ts` — детерминированный адаптер официального сайта ИР365. Читает категории с пагинацией, официальный WooCommerce Store API, sitemap и связанные проекты. HTTP GET ограничен `https://ir365.ru`; внешние редиректы и исполнение скриптов запрещены. При сетевой ошибке допустима одна повторная попытка. Другой производитель требует своего адаптера.

`src/features/agent-office/collector-contract.ts` — схема сырого результата. Каждое поле содержит исходную строку и официальный sourceUrl; отсутствующие значения — null. API-объекты, таблицы с колонками вариантов, тексты, характеристики и ссылки на фотографии сохранены без преобразования в модель публичного каталога. HTML/JSON источников и метаданные получения лежат в `runs/<runId>/sources`; отдельные проекты — `project-<officialId>.json`; общий результат — `result.json`. Фотографии — официальные URL, alt и srcset, без скачивания бинарных файлов. Количество санузлов/спален из косвенных признаков не вычисляется.

Событие `project.collected` записывается после сохранения проекта. Ошибки и неполное покрытие сохраняются явно; частичный результат не считается полным. Последующие агенты не запускаются, публичный каталог недоступен для записи. Разделы ниже описывают предыдущий этап Scout.

## Запуск и границы

Откройте `/agent-office` на локальном Vite-сервере, затем Tasks. Введите город и нажмите «Запустить Astra → Scout». Такое же поле есть в Overview агента Astra. После завершения JSON открывается прямо в Tasks и Files агента Scout кнопкой «Открыть JSON». Activity и Replay читают фактическую сохранённую историю, включая неудачные запуски.

Исполняются только Astra и Scout. Astra — детерминированный оркестратор в TypeScript; Scout — отдельный процесс установленного Codex CLI с настоящим `web_search="live"`. Остальные агенты остаются idle. У Publisher нет исполнительного обработчика. Runtime не импортирует никаких функций записи каталога и пишет только в свою папку.

Провайдер проверен с текущим Codex CLI, авторизованным через ChatGPT. Если он не установлен или не авторизован, интерфейс сообщает причину и не запускает фиктивный поиск. Для другого компьютера укажите `CODEX_EXECUTABLE` и выполните `codex login`. Дополнительный поисковый API не требуется при доступном web_search в CLI. Запуски используют доступ и лимиты текущего аккаунта Codex.

Процесс Scout запускается без shell (`spawn` с массивом аргументов), в `read-only`, без shell-инструмента, MCP-приложений, плагинов и делегирования. Пользовательская конфигурация CLI не загружается; используется стандартная модель CLI. Авторизация берётся штатным механизмом CLI, секреты в браузер и prompt не передаются. Город и снимок публичного реестра передаются как данные через stdin. Инструкция запрещает каталогизацию проектов, тексты, карточки, публикацию и выполнение инструкций с сайтов.

Это локальная система, не сервис на боевом хостинге. API подключается только через Vite `configureServer`; в production build его нет. Обработчик разрешает loopback-адреса, локальный Host и тот же Origin, запрещая доступ из локальной сети и чужих сайтов. Это ограничение локального прототипа, не полноценная пользовательская авторизация.

Сырые файлы runtime закрыты от прямой раздачи Vite через `server.fs.deny`, включая папку из `AGENT_RUNTIME_DIR`. Из браузера результат доступен только через локальный API.

## Файловая структура

`runtime/` исключён из Git. Каталог можно переопределить через серверную переменную `AGENT_RUNTIME_DIR`.

```text
runtime/
  .writer.lock                     один процесс записи
  tasks/<taskId>.json               задания Astra и Scout
  runs/<runId>.json                 основной снимок запуска и его история
  events/<runId>.jsonl              машиночитаемый журнал
  runs/<runId>/
    registry-before.json           реестр перед поиском
    registry-checked.json          актуальный реестр при проверке результата
    scout-instructions.txt         фактическая инструкция запуска
    provider.jsonl                 исходный журнал Codex CLI
    stderr.log                     диагностика CLI
    result.json                    проверенный структурированный результат
```

Основным источником восстановления является `runs/<runId>.json`; tasks, events и result — проекции. Запись выполняется во временный файл с последующим rename. После перезапуска незавершённый запуск получает фактическую ошибку прерывания; автоматический повтор не выполняется. Одновременно разрешён один запуск. Повтор HTTP-запроса с тем же requestId возвращает существующее задание.

Задания содержат ID запуска и родителя, город, исполнителя, статус, входные данные, путь к результату, источники, ошибку и временные отметки. Схемы Zod используются и сервером, и интерфейсом.

## Поиск, результат и дубли

Scout делает поисковые запросы и обращается к официальным страницам, не собирая полный каталог. Финальный JSON проверяется по двум уровням: JSON Schema для ответа CLI и Zod для runtime. Должен быть зафиксирован хотя бы один настоящий поисковый вызов. sourceUrl каждого кандидата должен присутствовать среди завершённых обращений веб-инструмента к URL и принадлежать тому же домену, что официальный сайт. Одного URL, упомянутого моделью в тексте, недостаточно. В журнале некоторых версий CLI открытие URL представлено действием `other` — адаптер учитывает этот формат, не принимая за открытие поисковую строку или незавершённый вызов.

У кандидата есть название, официальный сайт, город/регион, продукты, отдельные yes/no/unclear для домов и бань, производственная роль, подтверждённость по официальному сайту, URL и пересказ доказательства, confidence, причина включения и возможный ID существующей записи. `confidence` — оценка Scout, а не гарантированная вероятность. Отсутствие сведений обозначается unclear.

Перед принятием результата повторно читается настоящий `manufacturerRegistry` через Vite SSR, включая его актуальные незакоммиченные изменения. Сравниваются нормализованные домены (www, регистр, IDN, поддомены), ID и названия. Дубли, посредники и нерелевантные продукты попадают в `excluded` с причиной; новые кандидаты — в `candidates`. Для частичного совпадения похожих названий и разных доменов пока нужна ручная проверка. Собственное производство проверяется по заявлению официального сайта, а не по юридическому реестру. Полный охват города не гарантируется.

## События и интерфейс

Событие source.found фиксирует завершённое обращение инструмента к URL. CLI не передаёт адаптеру HTTP-статус и полный текст ответа: такое обращение может закончиться тайм-аутом. Scout обязан исключать неоткрытые страницы; окончательная проверка фактов остаётся следующим этапом Verifier. Кнопка «Открыть JSON» загружает результат с локального API, проверяет схему и показывает данные внутри панели.

Сохраняются `task.created`, `agent.assigned`, `agent.started`, `source.found`, `candidate.found`, `agent.completed`, `task.completed`, `task.failed`; используется прежний `task.handoff` и `file.recorded` для ссылки на результат. Все события имеют уникальный ID, runId, taskId, последовательность и время. Статусы карты выводятся из этих событий; ручное переключение статусов отсутствует.

Agent Office опрашивает `/__agent-runtime/snapshot` раз в секунду. После перезагрузки получает тот же журнал с диска. Replay применяет неизменяемый префикс событий к начальному состоянию; проигрывание не запускает агентов и не меняет текущую работу. Во время поиска линия передачи остаётся активной до завершения Scout. В Files и Tasks доступны только ссылки на фиксированный JSON-endpoint, произвольные пути не исполняются.

API:
- `GET /__agent-runtime/snapshot`
- `POST /__agent-runtime/tasks` с `{city, requestId}`
- `GET /__agent-runtime/runs/<runId>/result`

## Оставшиеся ограничения

Нет Collector/Extractor/Verifier/Editor/QA/Publisher/Watcher в исполнении, автоматической записи в каталог и развёртывания на хостинге. Нет фонового запуска после остановки Vite, очереди параллельных задач, автоматического retry и многопользовательского доступа. Один запуск ограничен 12 минутами. Нельзя считать все найденные компании окончательно проверенными: это кандидаты для ручного рассмотрения и следующего этапа Collector/Verifier. Ошибки CLI или несоответствие схеме заканчиваются task.failed, а не вымышленным успешным результатом.

Официальная документация используемого механизма: https://learn.chatgpt.com/docs/non-interactive-mode .

## Контракт полного пакета производителя

Единица передачи между уже существующими этапами — **производитель целиком**. Это runtime-конверт для сырья и аудита, а не новая модель публичного каталога. Выход подготовки использует поля существующих `Maker`, `Project`, `ProjectSourceFacts`; Platforma и BYGGE читаются из текущего реестра как примеры заполнения.

- Scout находит компанию и официальный сайт. Кандидат не заменяет данные компании.
- Collector обязан собрать компанию и весь официальный каталог домов/бань. Для компании явно учитываются контакты, описание, адрес/локация, технологии и география, логотип, социальные ссылки, юридические поля, объекты, отзывы, рабочее время и сертификаты. Отсутствие и невозможность проверки не скрываются.
- Конверт содержит данные компании, исходные проекты, источники фактов и изображений, охват каталога с датой, пропуски, конфликты, проверку дублей и статус. Дубли проверяются внутри пакета и относительно существующего реестра; варианты размеров изображений считаются кандидатами на проверку, не удаляются автоматически.
- Editor принимает только полный конверт. Прежние архивы из одних проектов остаются читаемыми, но новый запуск подготовки их отклоняет.
- `envelopeComplete` означает, что обязательные разделы обследованы и присутствуют; `dataComplete` и `ready` — отдельные признаки. Полный конверт с пропусками или конфликтами не объявляется готовым к публикации.
- Неизвестные значения остаются `null`. Отсутствие не означает ноль, отрицательный ответ или найденный статус. Юридическое лицо не выводится из имени оператора сайта; адрес города не заменяет точный адрес производства. Данные одного продукта/технологии не переносятся на другие по принадлежности одной компании.
- Каждый факт имеет официальный URL и доказательство; конфликтующие наблюдения сохраняются вместе, разрешённое значение остаётся `null`. Нормализация и исходные данные разделены.
- `POST /__agent-runtime/company-completions` с `{sourceRunId, requestId}` дополняет старый каталог данными компании. Данный путь не запускает Scout, не вызывает сборщик проектов и запрещает загрузку `/product/`, `/product-category/`, `/wp-json/`. Исходные проекты и их контрольная сумма сохраняются.
- `POST /__agent-runtime/preparations` принимает только завершённый полный пакет. Проверяет неизменность проектов, сохраняет подготовленные записи и полный исходный пакет в одном итоговом JSON, отдельно отчёт. Следующие агенты не запускаются.

Исполнители остаются прежними: Astra, Scout, Collector и Editor. Публичные файлы данных и визуализация не меняются. Исторический раздел ограничений выше описывает состояние первого запуска Scout, а не текущий набор подключённых этапов.
